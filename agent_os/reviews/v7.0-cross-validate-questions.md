# Agent OS v7.1 — 交叉验证问题集

> 日期：2026-06-29
> 背景：v7.1 架构已完成（基于 v7.0 + Anthropic 3 个月产品迭代分析）
> 当前代码：agent_os 6,096 LOC（含 v1.0 遗留）+ code-agent 840 LOC（独立项目）
> 目标：确定 Phase 0 实施前最后的关键决策

## v7.0 → v7.1 的主要变更

1. **新增「一B」章节**：2026 年 4-6 月 Anthropic 产品迭代的 5 个新教训
2. **上下文管道调整**：Phase 0 从 2 层→3 层（会话+项目+工具），长期记忆推迟到 Phase 2
3. **工具系统调整**：Phase 0 从 5 个→10 个工具
4. **代码量预算更新**：Phase 0 从 ~2,000→~2,500 LOC
5. **新增模块**：OTEL 隔离（Phase 1）、WIF 基础支持（Phase 2）
6. **终端 UI 策略**：Phase 0 用 Rich，Phase 2 评估 Textual 框架
7. **风险更新**：KAIROS 发布概率调高、新增 Fable 5 暂停风险

### 问题 1：战略选择 — "双模"是否是正确的核心差异化？

**v7.0 的核心主张**：
> 不做 Claude Code 的平替，做 Claude Code 的下一代。
> 双模（同步 + 异步）是核心差异化。

**但 2026 年 6 月的竞争格局变化**：
- Claude Code 泄露显示 KAIROS（异步守护进程模式）已实现但被编译标志隐藏
- Codex CLI v0.116.0 正在增加实时交互能力
- 双方都在向对方的方向移动

**我们的判断**：双模是正确方向，但窗口期可能只有 6-12 个月。

**问 ChatGPT**：
1. Claude Code 的 KAIROS 模式如果公开发布，会对"双模"差异化造成多大冲击？
2. Agent OS 的"双模"是否应该更激进——比如默认异步、同步作为调试模式？
3. 如果只能选一个模式先做（同步 or 异步），哪个更有长期价值？

**问 Gemini**：
1. Google 内部对 Agent 工作流的看法：实时交互 vs 异步委托，哪个是未来？
2. Gemini Code Assist 的 Agent Mode 是同步还是异步？Google 观察到了什么用户行为？
3. "双模"架构在工程上是否引入了不必要的复杂度？是否应该先做一个模式做到极致？

### 问题 2：MVP 范围 — Phase 0 应该做多大？

**v7.0 的 Phase 0 计划**（2 周，~2,000 LOC）：
```
Week 1: Engine Core (500 LOC) + Message History (300) + Tool Registry (300) + 5 Core Tools (500)
Week 2: Sync Mode (400) + Permission Racer (400) + Context Pipeline (400, 2层) + Terminal UI (400)
```

**之前的评审意见分歧**：
- ChatGPT（v4.0 评审）：MVP 12-15K LOC，先做 Runtime → Evaluation → Recovery → Evolution
- Google AI（交叉评审）：MVP 应该缩减到 5,000-8,000 LOC，砍掉 Failure Memory、简化 Validation、硬编码 Router
- v7.0 自己：15,000 LOC 总预算，Phase 0 = 2,000 LOC

**问 ChatGPT**：
1. v7.0 的 Phase 0 范围（2 周，2,000 LOC）是否合理？还是太激进/太保守？
2. 从你的 v4.0 评审到现在，行业有什么变化让你调整对 MVP 范围的判断？
3. "Engine Core 500 LOC" 这个估算——核心 Agent Loop 真的能 500 行搞定吗？Claude Code 的核心 loop 虽然只有 200 行，但它的消息管道、错误处理、流式响应加起来远不止这些。

**问 Gemini**：
1. Google 的 internal Agent 项目，从零到可用的 MVP 通常需要多少 LOC？
2. "先做同步还是先做异步"——从工程风险角度看，哪个路径更容易落地？
3. v7.0 的 Phase 0 把 Context Pipeline 放在 Week 2——上下文压缩是不是应该更早做？还是可以推迟？

### 问题 3：技术栈 — Python 终端 UI 是否足够？

**v7.0 的计划**：
- 终端 UI：Rich + Prompt Toolkit（800 LOC）
- 对比 Claude Code：React + Ink（60,000 LOC）

**风险**：
- Python 终端框架（Rich/Prompt Toolkit）的功能上限 vs React+Ink
- 响应式布局、实时更新、复杂交互——Python 能胜任吗？
- code-agent 已经用 Rich 实现了基础 CLI，但功能非常有限

**问 ChatGPT**：
1. Python Rich + Prompt Toolkit 能否支撑一个"Claude Code 级别"的终端 UI？还是说最终必须用 React+Ink 或 Web-based TUI？
2. 如果终端 UI 用 Web 技术（比如 Textual Web 或自建 WebSocket TUI），会不会更好？但这是否引入了不必要的依赖？
3. code-agent（840 LOC）的现有 CLI 代码有多少可以复用？还是应该完全重写？

**问 Gemini**：
1. Google 的 Gemini CLI 用了什么终端 UI 技术栈？Node.js 还是原生？
2. 从用户体验角度，终端 UI 的"最低可接受标准"是什么？一个简单的 REPL 够用吗？还是需要分屏、进度条、实时更新？
3. 如果 MVP 阶段用最简单的 REPL（read-eval-print loop），UI 增强留到 Phase 2，这个策略合理吗？

### 问题 4：上下文压缩 — 从几层开始？

**v7.0 的计划**：
- Phase 0：2 层（会话上下文 + 项目上下文）

**Claude Code 的参考**：

**问 ChatGPT**：

2. 上下文压缩的实现难度被低估了吗？Claude Code 花了 25,000 LOC 做这个——我们的 800 LOC 预算是否现实？
3. 有没有一种"最小可行上下文系统"的设计，可以在 300-500 LOC 内实现？

**问 Gemini**：
1. Google 的 Agent 系统如何处理上下文窗口限制？RAG？滑动窗口？分层压缩？
2. 对于编码 Agent，最关键的上下文信息是什么？（项目结构？最近修改？相关文件？）
3. 上下文压缩的"80/20 法则"是什么——20% 的代码解决 80% 的问题？

- `agent_os/`：6,096 LOC，"下一代 Agent 平台"
  - 有 v1.0 遗留代码（engine.py、event_bus.py、plugin_system.py 等）

**问题**：
- code-agent 的 Agent Loop 是否可以成为 agent_os Phase 0 的起点？

### 问题 6：15,000 LOC 预算是否现实？

**v7.0 的预算**：
```
Layer 0: Bootstrap      ~500 LOC
Layer 1: Engine        ~3,000 LOC
Layer 2: Services      ~5,000 LOC
Layer 3: Governance    ~3,000 LOC
测试:                  ~3,500 LOC
总计:                  ~15,000 LOC
```

**对比参考**：
- Claude Code：512,000 LOC TypeScript（等效 Python ~160,000）
- Codex CLI：~200,000 LOC Rust（等效 Python ~100,000）
- claw-code（Rust 重写 Claude Code）：~20,000 LOC
- code-agent：840 LOC

**问 ChatGPT**：
1. 15,000 LOC 对于"一个能用的编码 Agent 平台"来说，是低估了还是高估了？
2. 从你的经验看，哪些模块的 LOC 预算最容易被低估？（我猜是 Context Pipeline 和 Tool System）
3. 如果预算超了，应该砍什么？如果预算有余，应该加什么？

**问 Gemini**：
1. Google 内部类似项目的 LOC 密度如何？15,000 LOC Python 相当于 Google 标准的多少工程月？
2. 从工程管理角度，15,000 LOC 分 8 周完成（每周 ~1,875 LOC）——这个节奏合理吗？
3. 测试占比 23%（3,500/15,000）——对于 MVP 阶段，这个比例合理还是太高/太低？
