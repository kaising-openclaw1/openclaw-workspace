# Agent OS — 自进化系统架构设计 v1.0

> **版块**：Intelligence Layer — Evolution Manager
> **研究基础**：Claude Code 512K LOC 逆向工程 · ChatGPT × Gemini 交叉评审 · 2026 自进化 Agent 行业研究
> **核心理念**：不做 Claude Code 的平替，做 Claude Code 的下一代
> **设计目标**：一个可验证、可审计、可回滚的辅助进化系统

---

## 零、问题定义

### 0.1 为什么要自进化？

AI Agent 的核心悖论：**每次会话开始时，Agent 都从零开始。** 它不记得上次犯过的错误、不记得用户偏好的工作方式、不记得哪个工具调用模式最有效。

当前的解决方案：
- **Claude Code**：autoDream（记忆合并，隐藏 feature flag 后）
- **OpenAI Codex**：无公开的自进化机制
- **Cursor**：基于索引的代码库记忆，无行为级进化
- **Devin**：专有系统，细节未知

**我们的差异化机会**：在 MVP 阶段就引入可验证的自进化能力，而不是像 Claude Code 那样藏在 feature flag 后面。

### 0.2 自进化不是什么

| 不是 | 是 |
|------|-----|
| 模型权重自动更新 | 提示词 + 行为策略的辅助优化 |
| 无监督自我改进 | 人类审批的进化循环 |
| 全自动代码生成 | 参数级 + 策略级的渐进式调优 |
| 黑盒优化 | 可审计、可回滚的进化轨迹 |

### 0.3 设计约束

- **差异化窗口**：6-12 个月（ChatGPT × Gemini 共识）
- **首次进化实验**：必须极其简单（如调整 Executor Pool 并发数）
- **人类审批**：所有进化变更必须经过人类确认
- **可回滚**：任何进化变更都可以原子级回滚
- **可审计**：每次进化都有完整的决策日志

## 一、核心架构

### 1.1 四层进化循环

```
┌─────────────────────────────────────────────────────────────┐
│                    Self-Evolution System                     │
│                                                              │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌────────┐ │
│  │ Monitor  │───▶│ Analyzer │───▶│  Evolver │───▶│ Deploy │ │
│  │ (感知层)  │    │ (分析层)  │    │ (进化层)  │    │ (部署层) │ │
│  └──────────┘    └──────────┘    └──────────┘    └────────┘ │
│       │               │               │               │      │
│       ▼               ▼               ▼               ▼      │
│  ┌─────────────────────────────────────────────────────┐    │
│  │              System Knowledge（知识层）               │    │
│  │  进化历史 · 决策日志 · 失败模式 · 用户偏好 · 性能基线  │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                              │
│  ┌─────────────────────────────────────────────────────┐    │
│  │              Human Approval Gate（审批门）            │    │
│  │  所有进化变更 → 人类审批 → 部署 / 回滚               │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 模块职责

#### Monitor（感知层）~800 LOC

采集系统运行时的性能数据和行为数据。

```
采集维度：
├── 执行性能
│   ├── 任务完成时间（P50/P95/P99）
│   ├── LLM 调用延迟
│   ├── 工具调用成功率
│   └── Token 消耗
├── 错误模式
│   ├── 错误类型分布
│   ├── 重试次数分布
│   └── 失败链追踪
└── 行为模式
    ├── 工具使用频率
    ├── 参数分布
    └── 用户反馈信号
```

**关键设计决策**：
- 不采集用户代码内容，只采集行为元数据
- 数据本地存储，不上传
- 采样率可配置（默认 100% 关键指标，10% 非关键指标）

#### Analyzer（分析层）~1,200 LOC

识别性能瓶颈、错误模式和进化机会。

```
分析流程：
├── 1. 基线建立
│   └── 首次运行建立性能基线（P50/P95/P99）
├── 2. 异常检测
│   ├── 统计异常（超过 2σ 偏离基线）
│   └── 模式异常（新出现的错误类型）
├── 3. 根因分析
│   ├── 关联分析（错误与参数/工具/输入的关联）
│   └── 因果链追踪（错误传播路径）
└── 4. 机会识别
    ├── 参数优化机会（如并发数调整）
    ├── 策略优化机会（如重试策略调整）
    └── 行为优化机会（如工具选择偏好）
```

**关键设计决策**：
- 纯规则引擎 + 统计方法，不用 LLM 做分析（保证确定性）
- 分析结果以结构化的"进化提案"格式输出
- 每个提案附带预期收益评估和风险评分

#### Evolver（进化层）~1,500 LOC

生成进化方案，在沙箱中验证。

```
进化流程：
├── 1. 提案生成
│   ├── 参数级（调整配置参数）
│   │   └── 如：Executor Pool 并发数 3→5
│   ├── 策略级（调整行为策略）
│   │   └── 如：重试策略 固定→指数退避
│   └── 提示词级（调整系统提示词）
│       └── 如：增加"优先使用 Glob 工具"的提示
│
├── 2. 沙箱验证
│   ├── 回放历史任务（使用真实请求）
│   ├── 对比性能指标（进化前 vs 进化后）
│   └── 回归测试（确保不退化）
│
└── 3. 提案打包
    ├── 差异描述（变更了什么）
    ├── 验证结果（性能对比数据）
    ├── 回滚方案（如何回滚）
    └── 风险等级（低/中/高）
```

**关键设计决策**：
- 第一个进化实验必须是参数级（最简单的）
- 沙箱验证使用历史任务回放，不消耗 LLM API
- 提示词级进化需要 LLM 辅助，仅在 Phase 2 引入

#### Deploy（部署层）~500 LOC

执行进化部署，监控效果，支持回滚。

```
部署流程：
├── 1. 人类审批
│   ├── 展示进化提案（差异 + 验证结果 + 风险）
│   ├── 等待人类确认（超时默认拒绝）
│   └── 记录审批决策
│
├── 2. 灰度部署
│   ├── 低风险：直接全量部署
│   ├── 中风险：50% 流量灰度
│   └── 高风险：10% 流量灰度 + 24h 观察
│
├── 3. 效果监控
│   ├── 部署后 1h/6h/24h 自动检查
│   ├── 对比进化前后的性能基线
│   └── 检测退化信号
│
└── 4. 自动回滚
    ├── 退化超过阈值 → 自动回滚
    ├── 回滚后发送通知
    └── 记录回滚原因
```

**关键设计决策**：
- 人类审批是强制门禁，不可跳过
- 灰度部署支持流量百分比和持续时间配置
- 自动回滚阈值：P95 延迟增加 >20% 或错误率增加 >50%

#### System Knowledge（知识层）~1,000 LOC

存储进化历史、决策日志和系统知识。

```
知识结构：
├── 进化历史
│   ├── 每次进化的完整记录
│   ├── 决策理由
│   └── 效果数据
├── 失败模式库
│   ├── 已知错误模式
│   ├── 解决方案
│   └── 预防策略
├── 用户偏好
│   ├── 显式偏好（用户直接设置的）
│   └── 隐式偏好（从行为推断的）
└── 性能基线
    ├── 当前基线
    ├── 历史基线
    └── 退化检测阈值
```

**关键设计决策**：
- 所有数据本地存储（JSON + SQLite）
- 进化历史是 append-only 日志
- 用户偏好需要用户确认后才能生效

## 二、进化实验分级

### 2.1 三级进化实验

| 级别 | 范围 | 风险 | 示例 | 沙箱验证 | 灰度部署 | 人类审批 |
|------|------|------|------|---------|---------|---------|
| L1 参数级 | 配置参数 | 低 | 并发数 3→5 | ✅ 历史回放 | 全量 | ✅ 简单确认 |
| L2 策略级 | 行为策略 | 中 | 重试策略变更 | ✅ 历史回放 | 50% 灰度 | ✅ 详细审批 |
| L3 提示词级 | 系统提示词 | 高 | 增加工具偏好提示 | ✅ LLM 辅助验证 | 10% 灰度 | ✅ 详细审批 |

### 2.2 进化实验生命周期

```
创建 → 验证 → 审批 → 部署 → 监控 → (回滚 | 固化)
 │       │       │       │       │        │
 │       │       │       │       │        └── 效果确认后写入知识库
 │       │       │       │       │
 │       │       │       │       └── 退化检测 → 自动回滚
 │       │       │       │
 │       │       │       └── 灰度部署 → 监控窗口
 │       │       │
 │       │       └── 人类审批 → 通过/拒绝
 │       │
 │       └── 沙箱验证 → 通过/失败
 │
 └── Analyzer 识别机会 → 创建提案
```

## 三、与 Claude Code autoDream 的对比

| 维度 | Claude Code autoDream | Agent OS 自进化系统 |
|------|----------------------|-------------------|
| **触发条件** | 24h + 5 会话 | 性能退化检测 + 定时触发 |
| **范围** | 记忆文件合并/裁剪 | 行为参数 + 策略 + 提示词 |
| **验证** | 无 | 沙箱回放 + 回归测试 |
| **人类审批** | 无（自动执行） | 强制（所有级别） |
| **回滚** | 无（不可撤销） | 自动回滚 + 手动回滚 |
| **审计** | 无 | 完整进化历史日志 |
| **状态** | 隐藏 feature flag | 核心功能，MVP 即包含 |

**核心差异**：autoDream 是"记忆维护"，自进化系统是"行为优化"。前者是被动的、不可逆的；后者是主动的、可审计的、可回滚的。

## 四、技术实现

### 4.1 数据模型

```python
@dataclass
class EvolutionProposal:
    """进化提案"""
    id: str                    # 唯一标识
    created_at: float          # 创建时间
    level: str                 # L1/L2/L3
    target: str                # 进化目标（如 "executor.pool_size"）
    current_value: Any         # 当前值
    proposed_value: Any        # 建议值
    expected_benefit: str      # 预期收益描述
    risk_score: float          # 风险评分 0.0-1.0
    sandbox_result: dict       # 沙箱验证结果
    status: str                # pending/approved/rejected/deployed/rolled_back

@dataclass
class EvolutionRecord:
    """进化记录（append-only）"""
    id: str
    proposal_id: str
    action: str                # proposed/approved/rejected/deployed/rolled_back
    timestamp: float
    actor: str                 # "system" | "human:<name>"
    reason: str
    metrics_before: dict       # 进化前性能指标
    metrics_after: dict        # 进化后性能指标
```

### 4.2 存储架构

```
~/.agent-os/evolution/
├── proposals/          # 进化提案（JSON）
│   ├── prop_001.json
│   └── prop_002.json
├── history/            # 进化历史（append-only JSONL）
│   └── evolution.log
├── baselines/          # 性能基线
│   └── baseline_20260701.json
└── knowledge/          # 系统知识
    ├── failure_patterns.json
    └── user_preferences.json
```

### 4.3 关键接口

```python
class EvolutionManager:
    """进化管理器 - 对外接口"""

    async def propose(self, target: str, value: Any) -> EvolutionProposal:
        """创建进化提案"""

    async def validate(self, proposal_id: str) -> SandboxResult:
        """沙箱验证提案"""

    async def deploy(self, proposal_id: str, approved_by: str) -> bool:
        """部署进化（需要人类审批）"""

    async def rollback(self, proposal_id: str, reason: str) -> bool:
        """回滚进化"""

    async def get_history(self, limit: int = 100) -> List[EvolutionRecord]:
        """获取进化历史"""

    def get_current_baseline(self) -> dict:
        """获取当前性能基线"""
```

## 五、风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 进化导致性能退化 | 中 | 高 | 沙箱验证 + 灰度部署 + 自动回滚 |
| 进化循环失控 | 低 | 高 | 人类审批门禁 + 进化频率限制 |
| 用户偏好被错误推断 | 中 | 中 | 隐式偏好需要用户确认后才生效 |
| 沙箱验证不准确 | 中 | 中 | 使用真实历史任务 + 多轮验证 |
| 进化历史膨胀 | 高 | 低 | 定期归档 + 压缩策略 |

## 七、验证标准

### 7.1 首次进化实验（M3 里程碑）

**目标**：自动调整 Executor Pool 并发数

```
实验设计：
1. Monitor 采集 100 个任务的完成时间
2. Analyzer 检测到 P95 延迟 > 5s（基线 3s）
3. Analyzer 发现并发数 3 是瓶颈（CPU 利用率 < 40%）
4. Evolver 生成提案：并发数 3 → 5
5. 沙箱回放 100 个历史任务，验证 P95 延迟降低 > 20%
6. 人类审批
7. 全量部署
8. 24h 监控：P95 延迟降低 25%，无退化信号
9. 固化到知识库
```

### 7.2 成功指标

| 指标 | 目标 |
|------|------|
| 进化提案准确率 | > 80%（沙箱验证通过率） |
| 进化部署成功率 | > 90%（部署后无退化） |
| 自动回滚准确率 | 100%（退化检测无漏报） |
| 人类审批时间 | < 5 分钟（低风险提案） |
| 系统知识积累 | 每 1000 个任务至少 1 个进化提案 |

## 八、与 ChatGPT × Gemini 共识的对照

| 共识点 | 本设计 | 状态 |
|--------|--------|------|
| "第一个进化实验必须极其简单" | Executor Pool 并发数调整 | ✅ |
| "自我调优在 Week 7-8 引入" | M3 Week 5-6 引入（更激进） | ⚠️ 提前了 |

| "Introspection + Evolution Memory 合并为 System Knowledge" | 合并为 System Knowledge | ✅ |
| "不做 Consensus Gate" | 不做 | ✅ |
| "Python + mypy strict mode" | Python + Pydantic | ✅ |
| "可审计、可回滚" | append-only 日志 + 自动回滚 | ✅ |

## 九、开放问题

1. **进化频率**：多长时间触发一次进化扫描？定时（每小时）？事件驱动（性能退化时）？还是混合？
2. **进化优先级**：当同时有多个进化提案时，如何排序？按预期收益？按风险？按用户偏好？
3. **多项目隔离**：如果 Agent OS 同时服务多个项目，进化数据是否需要隔离？
4. **进化策略迁移**：L1 参数级的进化经验能否用于指导 L2 策略级进化？
5. **冷启动**：首次运行时没有历史数据，如何建立基线？
